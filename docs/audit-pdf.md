# The papers reader — audit

Judged the way Drawboard PDF, PDF Expert or Preview would be judged: not "the
happy path works" but every tool correct in every state, on every file, on
every device, and never losing anybody's work.

**Nothing in the reader was changed while auditing.** The only files written
are this one and ten generated papers under `public/papers/audit/`, which are
fixtures and can be deleted.

---

## How this was run

Everything below was **driven in a real browser**, never read out of the
source. Real Chromium and real WebKit, real pointer and touch input, at four
surfaces: laptop 1440x900, iPad landscape 1194x834, iPad portrait 834x1194,
phone 390x844. The rig starts the project's own harness — the real bundle, the
real reader, the real Supabase client, fixtures only at the far end of the
wire — and injects papers through `HARNESS_REAL_PAPER`, the hook
`tests/harness/postgrest.js` already provides.

**Every finding was reproduced twice**, the second time from a clean reload in
a fresh browser context. Anything that would not reproduce is in *Would not
reproduce* at the end.

### The papers it was run against

A reader is only as good as the worst thing somebody opens in it, and the repo
ships one good 14-page paper. Ten were generated by hand as raw PDF, because
this repo has no PDF writer:

| file | what it is |
|---|---|
| `one-page.pdf` | a single page, nothing before or after it |
| `no-text.pdf` | two pages of drawing and no text layer at all — a scan |
| `mixed-rotation.pdf` | four pages at 0, 90, 180 and 270 degrees |
| `mixed-size.pdf` | Letter, A4 landscape, A3, a 283x425 slip, Letter |
| `many-pages.pdf` | 320 pages, each repeating a phrase that appears on all of them |
| `corrupt.pdf` | a real header and rubbish where the body should be |
| `encrypted.pdf` | declares `/Encrypt` |
| `arabic.pdf` | extracted text is genuinely Arabic |
| `cjk.pdf` | extracted text is genuinely CJK, with no spaces anywhere |
| `pre-annotated.pdf` | carries its own `/Highlight` and `/Text` annotations |

Verified against pdf.js before use, so a fixture rejected for the wrong reason
could not be mistaken for a reader fault.

### What these fixtures cannot cover, and why

- **Arabic and CJK glyph shaping.** Embedding an Arabic or CJK font by hand
  means writing a TrueType subset. These files carry a real `/ToUnicode` map
  instead, so the **extracted** text — what marks anchor to, what search reads,
  what a screen reader speaks — is genuinely Arabic and genuinely CJK, while
  the rendered glyphs are Latin placeholders. That covers extraction order,
  selection direction, anchor round-tripping and text-layer alignment, which
  is the half this reader owns. It does not cover shaping, ligatures or bidi
  **rendering**, which are pdf.js's.
- **A correctly encrypted file.** Writing one by hand means implementing the
  standard security handler's key derivation. `encrypted.pdf` declares
  `/Encrypt`, which is the branch pdf.js takes before any key is used — enough
  to test what the reader does when a document says it is protected.
- **A real scan.** `no-text.pdf` is vector drawing with no text layer, which is
  what a scan is to this reader. It is not a photograph of a page, so it says
  nothing about raster size or memory on a real scanned manual.

## Findings

Ranked: **P0** loses work or leaks data between students · **P1** a mark lands
in the wrong place, or a tool cannot be finished or escaped · **P2** possible
but wrong, slow or confusing · **P3** polish. Within a severity, ordered by
how likely one of eleven students is to hit it in their first week.

### P1-1 · The reader opens armed to draw, so the first drag scribbles instead of selecting

**Reproduce.** Open any paper. Touch nothing else. Drag across a line of text.

**Observed.** On arrival the root carries `data-tool="hl"`, `data-draw="1"`,
`data-sel="0"`. The drag selects nothing — `getSelection()` is empty, the
selection pill does not appear — and leaves a highlighter stroke across the
words. Reproduced twice, both from a clean load.

**Expected.** The first gesture on a document is a selection in every reader I
know. Either the Select tool is armed on arrival, or the armed drawing tool is
unmistakable before the student's first drag.

**Where.** The default is the handed-over tool table:
`src/components/paper/v6/part3.js`, `let S=ctx.settings({tool:'hl',…})`, and
`hl` is in `DRAWS`, so `mode()` sets `data-draw="1"` and `data-sel="0"`.

**Note the disagreement.** This is the design's own default, not a
transcription error — so it is reported as a disagreement rather than a bug:
the handed-over file arms a drawing tool, and the standard this is being held
to says the cursor is the tool a reader opens with.

### P1-2 · A paper with no text layer offers six tools, four of which cannot work, and says nothing

**Reproduce.** Open `no-text.pdf` (two pages of drawing, no text). Arm the
Select tool. Drag across the page.

**Observed.** The pages render. The text layer has **zero** spans. All six
tools on the bar are enabled — `hand`, `pen`, `hl`, `era`, `note`, `ask` — and
so are Underline, Strikethrough, Flag and Text in the chest. Dragging with the
cursor selects nothing and no pill appears. Nothing anywhere says why.
Meanwhile the panel's empty state reads **"Yours would be the first — select a
line and mark it, and it will be here"**, which is an instruction the student
cannot follow on this file. Reproduced twice.

**Expected.** A tool that cannot work on a given file disables itself with a
reason. On a scan, every text tool should be visibly unavailable and the empty
state should say the paper has no text to select rather than telling the
student to select some. Pen, marker, highlighter, shape and snapshot all still
work and should stay.

**Where.** Nothing reads the text layer's emptiness:
`src/components/paper/v6/SheetPage.jsx` hands `onText(pageNumber, null)` when
the runs and spans do not line up, and `src/components/paper/v6/marks.js`
treats a page with no spans as "not ready yet" rather than "has no text" —
they are indistinguishable to it.

**Who hits it.** Anyone who uploads a scanned manual, which for Part-66
material is most of them.

### P2-1 · An encrypted paper and a corrupt paper give the same message, and it is wrong for one of them

**Reproduce.** Open `encrypted.pdf`. Then open `corrupt.pdf`.

**Observed.** Both show, byte for byte: *"This paper would not open. The
original still will, and everything marked on it is safe. Open the original"*.
The console shows `PasswordException` for the first and `InvalidPDFException`
for the second. Reproduced twice.

**Expected.** A password-protected paper is not broken — it needs a password,
and a reader should ask for one, or at least say that is what is wrong.
Telling a student the file "would not open" when it opens fine with a password
sends them to re-upload a file that was never damaged.

**Where.** `src/components/paper/v6/ReaderV6.jsx`, the paper-loading effect:
one `catch` sets one message for every failure.

### P1-3 · Reopening a paper you have read shows an empty screen

**Reproduce.** Open any paper. Scroll down with the wheel until you are a
dozen pages in. Reload the page (or leave and come back to the same paper).

**Observed.** The stage is **100% empty** — no page overlaps the visible
window at all — while the counter reads `012 / 320`. The reader has restored
the *memory* of page 12 (pages 10 to 14 are mounted and their canvases are
drawn) but `scrollTop` is 0, which is above all of them, so the student is
looking at spacer. Waiting does not fix it. Scrolling down three ticks leaves
it **still 100% empty** and drives the counter *backwards* to `006 / 320`.

Reproduced twice from a clean context, and not only on a synthetic fixture:
the same thing happens on **`M1.DEV`, the real 14-page paper** — left at
`09 / 14`, came back to `09 / 14` with nothing on screen.

| | counter | pages overlapping the window | blank | scrollTop |
|---|---|---|---|---|
| before the reload | 012/320 | 12, 13 | 2% | 10803 |
| after the reload | 012/320 | none | **100%** | 0 |
| after nudging down | 006/320 | none | **100%** | 1800 |

Screenshot: `scratchpad/audit/shot-reload-blank.png` — full chrome, correct
counter, no paper.

**Expected.** Either come back to where you were reading, or come back to page
one. Restoring the page number without restoring the scroll leaves the student
staring at nothing with a counter insisting they are on page 12.

**Where.** The remembered page is applied to the page *window* but never to
the stage's scroll offset; observable as mounted pages 10–14 sitting at a
scroll position of 0 in a 304513px scroll height.

**Who hits it.** Everyone, the second time they open a paper.

### P1-4 · The End key leaves the reader on a blank screen it cannot scroll out of

**Reproduce.** Open a long paper. Click once on the page. Press `End`.

**Observed.** `scrollTop` goes to the true bottom (304513 of 304513). The
mounted window does not follow — pages 15 to 19 stay mounted and drawn near
the top of the scroll height. Nothing overlaps the window: **100% blank**.
Waiting six more seconds changes nothing.

Scrolling is not a way out. Six ticks up: still 100% blank, counter now
`029/320`. Twelve ticks back down: still 100% blank, counter now `041/320`.
The counter climbs through the paper while the screen stays empty. Reproduced
twice from clean loads. Screenshot: `scratchpad/audit/shot-end-key.png`.

**Expected.** `End` goes to the last page, or does nothing. It should never be
able to put the reader somewhere it cannot get back from.

**Related, same key set.** `Home` is inconsistent between two runs of the same
gesture: pressed after a wheel scroll it did nothing at all (scroll stayed at
18007), and pressed after a click it moved the scroll to 0 while leaving the
counter reading `027/320`.

### P2-2 · There is no way to go to a page number in a 320-page paper

**Reproduce.** Open a 320-page paper. Try to get to page 212.

**Observed.** The whole of the control tray is: `−`, a zoom readout, `+`,
`Fit`, rotate left, rotate right, bookmark, and the island's *last five*
deck. There is no page field and no page list — the Pages tab in the panel
lists pages but the counter itself is not an input. Wheel scrolling from page
1 to page 212 is roughly 190 full-window scrolls. Reproduced twice.

**Expected.** A reader holding a 320-page manual lets you type a page number.

**Where.** Observed in the tray's own DOM, which holds exactly seven controls
and no `input` of any kind.

### P0-1 · Any student can read every other student's marks, notes and progress with the key from their own browser

**Reproduce.** Open wingman.institute in any browser. View source on
`/assets/index-CYZYMxNW.js` and search for the Supabase anon key — it is in
there twice. Then, from anywhere, with no login and no session:

```bash
curl -s "$SUPABASE_URL/rest/v1/paper_annotations?select=*" \
  -H "apikey: $ANON_KEY" -H "Authorization: Bearer $ANON_KEY"
```

**Observed.** Every row comes back. The request carries no student identity of
any kind — only the public key — so there is nothing for the database to
filter on, and it does not filter. One real annotation row returned in full:

| field | what came back |
|---|---|
| `author_id` | `user_3I2iHG…` — the marker's Clerk id, in the clear |
| `anchor` | 278 characters including `quote`, `prefix`, `suffix` — **the exact words they marked** |
| `body`, `hint` | the note text |
| `ring`, `colour`, `kind` | which ring it was posted to, and how it was tagged |
| `anonymous` | `false` — and it is a column on a row anyone can read |

Counts an anonymous caller can enumerate today, by asking for an exact count:

| table | rows readable |
|---|---|
| `paper_annotations` | 1 |
| `paper_ink` | 2 |
| `user_progress` | 5 |
| `pilot_profiles` | 3 |
| `lesson_threads` | 2 |
| `lesson_replies` | 3 |
| `chapter_completions` | 1 |

Reproduced twice. The numbers are small only because there are no students
yet; the mechanism does not change with eleven of them.

**Expected.** A mark posted to the private ring should be reachable by its
author and nobody else, whichever door you knock on. Going around the UI
should not be a way around the rule.

**Where.** Not a reader bug — the reader asks `paper_marks_for` and behaves.
It is the table underneath: `CLAUDE.md` states the design plainly, *"RLS is
enabled on every table with open `using (true)` policies, because the Supabase
client is anonymous from Postgres' point of view and access control happens in
the app."* That holds for as long as everyone uses the app.

**Two things make this worse than a private highlight being readable.**

1. **The brief promises anonymity that the wire does not deliver.**
   `docs/reader/BRIEF.md` §6.2 is explicit: questions are anonymous by
   default, because *"a student will not ask the thing they are actually
   confused about if their name is on it in front of the whole module"* — and
   it warns, in the same section, **"do not promise anonymity you don't
   deliver."** The `author_id` sits on the row next to the `anonymous` flag,
   readable by anyone holding the public key. A student who asks an anonymous
   question on a passage has their name on it for any classmate who looks.

2. **`user_progress` is in the same condition**, so it is not only reading
   marks — it is every student's whole progress blob.

**What I could not test, and the command that would finish it.** Whether the
same key can **change or delete** another student's marks. The probe writes to
the production database, so it was refused by this session's safety
classifier, and I did not work around it. It is the one question left, and it
is the difference between a privacy failure and a data-destruction one. The
script is written and read-only-safe apart from rows it creates and removes
itself:

```bash
node "/private/tmp/claude-501/-Users-hassa-Documents-Project-Wingman/ed66aa1c-f135-4b96-8fe4-4c8ea6d03425/scratchpad/audit/a8c.mjs"
```

It inserts two marks under invented author ids (`audit_alpha_DELETEME`,
`audit_bravo_DELETEME`), tries to edit and delete one of them as a caller that
owns nothing, and deletes both afterwards. It touches no real row.

## The eight tool guarantees

Driven tool by tool, twice, in a real browser.

| guarantee | verdict | evidence |
|---|---|---|
| Armed tool is unmistakable | **passes** | each of the six sets `data-tool`, lights exactly one button, and swaps the stage cursor — Pen and Highlight carry their own drawn SVG cursors at their own nib sizes |
| No tool arms silently | **passes** | 6 tools armed in turn, the state never changed without a click |
| Never two armed at once | **passes** | all 30 ordered pairs armed back to back; never more than one lit |
| Arming mid-selection corrupts nothing | **passes** | pen armed with the pointer still down mid-drag: marks 3→3, ink strokes 1→1, selection cleared, pill closed. Measured against a baseline |
| Navigating away discards cleanly | **passes** | see P1-3 for what it *does* break — but nothing is left behind |
| What you drew is where you tapped | **passes** | every mark-placement case below landed on its own words |
| Every action undoable in order | **partly** — see P1-5 | ⌘Z on a laptop is correct; there is no undo at all on a tablet |
| Nothing lost by reload | **passes for marks** | marks and ink come back on their words; the reading position does not (P1-3) |
| A tool that can't work disables itself | **fails** | P1-2 |

### P1-5 · On a tablet there is no way to undo anything, and no way to pinch to zoom

**Reproduce.** On a touch tablet (1194x834, touch on), open a paper. Tap a
word, mark it. Now try to undo it. Then try to pinch the page larger.

**Observed.**

- **Two-finger tap does not undo.** Marks stayed at 5. Dispatched as two real
  touch points, not a synthetic event.
- **Three-finger tap does not redo.** Marks stayed at 5.
- **There is no undo or redo button anywhere on the tablet** — searched every
  `button` in the document for an undo or redo label and found none.
- **Pinch does not zoom.** A full two-finger spread across the page left
  `--pw` at `720px` and the rendered page at 616px wide, unchanged.

So the only undo is ⌘Z on a hardware keyboard, and the only zoom is the `+`
and `−` inside the tray. Reproduced twice.

**Expected.** `docs/reader/BRIEF.md` §Undo asks for exactly this and is
specific: *"Buttons in the bottom bar, always visible. ⌘Z / ⇧⌘Z. Two-finger
tap = undo, three-finger tap = redo on touch."* None of the three touch
affordances exists. A reader on an iPad cannot take back a mis-stroke.

**What made this a substitution, and why.** WebKit will not let a script
construct a `Touch`, so the two- and three-finger taps were dispatched through
Chromium's input protocol on a touch-emulating tablet context rather than in
Safari. Single-finger behaviour was checked in real WebKit and matches. A real
iPad should still be checked before release, because Safari's own gesture
recognisers can claim a pinch before the page sees it.

### P2-3 · Escape does not put an armed tool down

**Reproduce.** Arm the Pen. Press `Escape`. Then click the lit Pen button
again. Then click empty space beside the paper.

**Observed.** `data-tool` stays `pen` through all three. Same for the Eraser
and the Note. The only ways out are arming a different tool, or the keyboard
letter `v`, which arms Select (undocumented on screen). Reproduced twice.

**Expected.** Escape is the universal way to put a tool down. Its absence is
felt most on a tablet, where the letter shortcut does not exist either.

### P2-4 · Every control on the reader is under the 44px this project mandates, and the one that opens zoom is 18px tall

**Reproduce.** On a tablet, measure the tool buttons and the page counter.
Measured as the actual tap target — probing outwards from each edge with
`elementFromPoint` until the hit stops being the button — not the drawn box.

| control | drawn box | real tap height |
|---|---|---|
| Select, Pen, Highlight, Eraser, Note | 38 × 38 | **41** |
| Ask, and the bar-editor button | 38 × 38 / 30 × 30 | **43** |
| the page counter `#cnt` — the only way into zoom, rotate, bookmark and the island | 53 × 18 | **18** |

The transparent `::before` does pay part of the tap floor back, which is why
41 and not 38, but it stops short. Reproduced twice.

**Expected.** `CLAUDE.md` states the rule without qualification: *"Every
button in this app is at least 44px on its shortest side (§12, enforced
globally in App.jsx)."* The reader is the one surface that does not obey it,
and it is the surface most likely to be used on glass.

### P0-2 · A mark made offline is lost, and the reader tells the student it is saved

**Reproduce.** Open a paper. Go offline (aeroplane mode, or a dead campus
wifi). Select a line and highlight it. Come back online. Reload.

**Observed.** The highlight appears on the page and in the panel. The word
**"Offline"** appears in the chrome, and the message reads **"Offline — marks
are saved here"**. Then:

| checked | result |
|---|---|
| anything queued in `localStorage`? | **nothing** — no key matching mark, ink, queue, pending, paper or reader |
| after 30 seconds back online, with `online`, `focus` and `visibilitychange` all fired | still only in memory; **no `paper_annotations` POST ever goes out** |
| after a reload | **the mark is gone** |
| the same mark made online, as a control | **survives** |

Reproduced twice, each from a clean context. The console shows the write
failing at the moment it is made (`net::ERR_INTERNET_DISCONNECTED`), and
nothing retries it.

The banner appears **because** the write failed — go offline and touch
nothing, and no banner appears at all. So the one moment the student is told
their work is safe is the exact moment it has just been lost.

**Expected.** Either queue the mark and flush it on reconnect, or say plainly
that it could not be saved. Saying "marks are saved here" when there is no
"here" is the worst of the three.

**Who hits it.** Anyone reading on a train, in a hangar, on campus wifi that
drops. For a Part-66 student with a tablet in a workshop this is the normal
case, not the edge case.

### P3-2 · Two tabs on the same paper do not see each other until a reload

**Reproduce.** Open the same paper in two tabs as the same student. Mark a
line in tab two.

**Observed.** Tab two sees tab one's earlier mark on load. Tab one never sees
tab two's new mark — checked four seconds later. Reload tab one and both are
there. Reproduced twice. Nothing is lost; it is only stale.

## What held up

Worth saying plainly, because an audit that only lists failures is not a
picture of the thing.

- **Marks land on their words, everywhere I could put them.** Created,
  reloaded, and confirmed the quad's centre still falls inside a text span
  containing the marked words: on a plain page, at the maximum zoom the reader
  offers, on a page rotated 90° and again at 180°, in Arabic, and in CJK with
  no spaces anywhere. Twice each.
- **An anchor round-trips exactly.** An Arabic mark came back as the same
  string, byte for byte, after a reload.
- **Marks unmount and come back correctly.** Scrolled fourteen pages away
  until the quad was destroyed, scrolled back: one quad, on `PAGE 1 OF 320`,
  the words it was made on.
- **Undo and redo are correct on a laptop.** Three marks made, ⌘Z three times
  took them back one at a time in order, a fourth did nothing rather than
  eating somebody else's mark, and ⇧⌘Z restored two.
- **Mixed page sizes are respected.** Letter, A4 landscape and A3 each keep
  their own aspect ratio to three decimal places, canvas matching box.
- **Switching papers fast does not break it.** Five papers opened 650ms apart,
  each abandoned mid-load: no error state, and it settled correctly on the
  last one.
- **Marking then reloading 120ms later keeps the mark.** So does backgrounding
  the tab the instant the write starts.
- **The page window is honest under a wheel.** Scrolling through 320 pages,
  the counter and the mounted window tracked together at every sample.
- **No mark is ever relocated.** The paper was replaced underneath three
  different ways — a different document, a longer one sharing no words, one
  with no text layer at all — and not once did a quad land on words the
  student had not marked. R1's first clause holds exactly. Against a control
  where the file is left alone, the mark comes back on its own words.
- **Text contrast passes in all twelve livery and variant combinations.**
  Page counter 15.97:1, filter chips 6.70:1, mark-card author 5.18:1,
  measured from painted pixels. Only the icons fall short (P2-8).
- **Every button has a name.** Forty-five buttons in the reader, zero without
  an accessible name, and a real 2px focus ring. Tab order runs the chrome
  then the rail, in the order they are drawn.

### P1-6 · The Text tool does not make a text box, and what it does make disappears on reload

**Reproduce.** Open the bar editor, add **Text** from the Draw tab, arm it.
Drag a box on the page. Type `torque values for the tail rotor`. Click away.
Reload.

**Observed.** No text box appears and the typed words go nowhere — searched
the whole document for the string afterwards and it is not there. What the
drag does instead is create a mark anchored to whatever paper text happened to
be under it: the mark count goes 3 → 4 and the new mark's quoted text is `for
dynamically-typed language`, which is the paper's words, not the student's.

On reload the mark count goes back to 3. The record is gone, with no error
shown at any point. Reproduced twice.

The wire shows why it is worth checking against production separately: the
insert goes to `paper_annotations` with `kind:"text"`, and `kind` is a
CHECK-constrained column. A CHECK violation on this stack returns a null row
rather than an error, which is exactly what a silently vanishing mark looks
like.

**Related, and unrun.** `supabase/migrations/0020_reader_tools.sql` is written
and **has not been run**. Confirmed read-only against the live project: both
columns it adds are absent.

```
paper_ink.variant   -> column paper_ink.variant does not exist
paper_ink.opacity   -> column paper_ink.opacity does not exist
paper_ink.tool      -> present
```

So the database in front of students today is the 0017 shape. Until 0020 runs,
there is no column in which a shape can record that it is a shape, and no
widened tool list.

### P2-5 · The Shape tool draws a line and saves as a pen stroke

**Reproduce.** Add **Shape** from the Draw tab. Its icon is a rectangle and a
circle. Arm it and drag on the page. Reload.

**Observed.** The drag draws a **straight line**, not a rectangle or a circle.
It is written to `paper_ink` as `tool:"pen"`, `colour:"blue"` — byte-identical
in kind to a Pen stroke — and comes back after a reload as a pen path. There
is nothing stored anywhere that records it was meant to be a shape.
Reproduced twice.

## What I could not test, and why

Named rather than hidden, as asked.

1. **Whether the anon key can change or delete another student's marks.**
   Attempted **twice**, and refused both times by this session's safety
   classifier because it writes to the production database. I did not work
   around it. **This is the most important open question in the audit**, and
   it is the one thing here that only you can settle.

   The second version is tighter than the first: it seeds from a real paper id
   so the insert is not rejected for the wrong reason, removes its two rows by
   exact primary key rather than a `LIKE` pattern, and brackets the whole run
   with a count of the table so any collateral would show.

   ```bash
   node "/private/tmp/claude-501/-Users-hassa-Documents-Project-Wingman/ed66aa1c-f135-4b96-8fe4-4c8ea6d03425/scratchpad/audit/a32-write.mjs"
   ```

   It prints the row count before and after, inserts two marks under invented
   author ids, tries to READ, EDIT and DELETE one of them as a caller that owns
   nothing, then deletes both. If EDIT or DELETE returns a changed row, the
   leak in P0-1 is not only a reading one and the ranking of this audit
   changes.
2. ~~Contrast across the six liveries, light and dark.~~ **Now measured** —
   see P2-8, done from painted pixels across all twelve livery and variant
   combinations. The paragraph below records the method that failed first, and
   why no claim here rests on it.

   *Superseded:* the first attempt was abandoned rather than reported wrong. The chrome's surfaces are translucent
   with backdrop filters, so walking computed styles to find the real
   background behind a label gives numbers that invert between light and dark
   — the page counter measured 1.19:1 in light and 18.28:1 in dark, which the
   screenshots contradict. This needs a real contrast tool sampling rendered
   pixels, or an eye. **No contrast claim in this document should be trusted.**
   Separately and reliably: **there is no livery control in the reader's
   tray** — it holds zoom out, zoom in, Fit, rotate left, rotate right,
   bookmark, and the page number, and nothing else.
3. **A real iPad and a real pencil.** Multi-touch gestures had to be dispatched
   through Chromium's input protocol because WebKit will not let a script
   construct a `Touch` (P1-5). Palm rejection, pencil pressure and tilt, and
   Safari's own gesture recognisers are untested.
4. **Arabic and CJK rendering.** The fixtures carry genuine Arabic and CJK
   *extracted* text with Latin placeholder glyphs, because embedding a real
   Arabic font by hand means writing a TrueType subset. Extraction order,
   selection, anchoring and round-tripping are covered. Shaping, ligatures and
   bidi rendering are not.
5. **A correctly encrypted PDF.** `encrypted.pdf` declares `/Encrypt`, which
   is the branch pdf.js takes before any key is used. A file with a real
   standard security handler was not built.
6. **A real scan.** `no-text.pdf` is vector drawing with no text layer, which
   is what a scan is to this reader, but it is not a photograph — so it says
   nothing about raster memory on a genuinely scanned manual.
7. ~~Orphaning when the paper changes underneath.~~ **Now tested** — see
   P1-10. Reached by pointing the paper at a file swapped on disk between two
   visits with the harness left running, so the marks survive while the paper
   does not.
8. **Eleven students at once.** Attempted twice and abandoned rather than
   reported. Eleven browser contexts were opened against the harness on one
   paper — first simultaneously, then staggered by 400ms the way a class
   actually arrives. Simultaneously, **none of the eleven finished loading the
   bundle at all** in either run (no page errors, the reader simply never
   mounted, 42 seconds in). Staggered, the run produced no result in twenty
   minutes and was stopped.

   That number measures a single-threaded Vite dev server transforming modules
   on demand for eleven clients on one laptop. It says nothing about eleven
   students against Vercel and Supabase, and reporting it as a reader failure
   would be wrong. **What stays untested is the part worth knowing:** whether
   eleven authors' marks all arrive, whether each student sees the other ten,
   and what a paragraph looks like with eleven overlapping highlights on it.
   Doing it honestly needs a production build served statically, or a staging
   deploy.

### P1-10 · When a paper changes underneath, every mark on it disappears and the reader says you never made any

**Reproduce.** Mark a line. Replace the paper's file while the paper's id and
version stay the same — a re-upload, or a re-extraction. Reopen it.

**Observed.** The good half first: **nothing is relocated.** No quad is drawn,
nothing lands on the wrong words. That is R1 of the brief, and it holds.

The bad half: the mark is **not listed anywhere**. `window.WM.marks` is empty,
the panel's own tab reads **"Marks 0"**, and the empty state says *"Yours
would be the first — select a line and mark it, and it will be here."*

And the mark is not gone. Watching the response to `paper_marks_for` on that
same load:

```
paper_marks_for -> 1 row, quote "that"
```

The database still has it. The reader receives it, cannot place it, and drops
it in silence. Reproduced twice, against a control where the file is left
alone and the mark comes back correctly on its own words.

| the file underneath | mark still stored | drawn | listed as lost |
|---|---|---|---|
| unchanged (control) | yes | **yes, on its words** | n/a |
| replaced with a different document | yes, on the wire | no | **no** |
| replaced with a longer one sharing no words | yes, on the wire | no | **no** |
| replaced with one that has no text layer | yes, on the wire | no | **no** |

**Expected.** The brief's rule is two clauses and only the first is
implemented: *"A lost mark is orphaned, never relocated. `resolveAnchor`
returns null rather than guessing, **and the reader lists what lost its
place**."* There is no such list.

It also breaks the Voice rule in `CLAUDE.md` — *"Never state absence or a zero
count"* — in the worst available way, by stating a zero that is false.

**The mitigating fact, and it matters.** The work is not destroyed. Put the
original file back and the marks return. This is a display failure, not a data
one, which is why it is P1 and not P0.

### P2-8 · Tool icons are below the contrast floor in all six liveries, and the armed one is the worst

## Verdict

**Not ready.** The reading and marking core is genuinely good, and that is the
reason to fix rather than rebuild: marks land on their exact words at every
zoom, on rotated pages, in Arabic and in CJK; memory is flat across 320 pages;
undo is correct on a laptop; six of the eight tool guarantees hold under every
abuse I could throw at them; and when a paper is replaced underneath, not one
mark is relocated onto the wrong words.

What stops it is not the reader. It is that **every student can read every
other student's marks, notes and progress with a key that ships in the public
bundle**, while the brief promises those questions are anonymous — and that a
mark made with no signal is destroyed while the screen says it was saved.

**The one thing that decides it:** whether a student's marks are private and
durable. Everything else on this list is a few weeks of work on a reader that
is already close. That one is a database question, and until
`paper_annotations`, `paper_ink` and `user_progress` stop answering an
anonymous caller, nothing built on top of them can go in front of eleven
people who have been told their questions are anonymous.

## Ten tests to add

Mechanisms, not patches — each one fails today and would keep failing if the
fix regressed.

1. **`check:paper-db` gains a stranger.** As a caller holding only the anon
   key, `GET /paper_annotations?select=*` must return **zero** rows belonging
   to anyone else, and the same for `paper_ink` and `user_progress`. Extend
   the existing real-database suite, which already writes as two accounts and
   cleans up after itself.
2. **A stranger cannot write.** The same caller attempts `PATCH` and `DELETE`
   on a mark it does not own; both must be refused. This is the question
   P0-1 leaves open, made permanent.
3. **Anonymity is anonymity.** Post a question with `anonymous: true`, then
   read it back as another student through every door — the function and the
   table. The author id must not be in either answer.
4. **Offline round trip.** With the network cut, make a mark; restore the
   network; reload. The mark must be there. The test must fail if the write is
   dropped *and* if the reader claims it was saved when it was not.
5. **Reopening lands on paper.** Scroll a paper to page 12, reload, and assert
   that at least one page box overlaps the stage's visible window. A blank
   stage fails. This one assertion catches P1-3 and P1-4 together.
6. **Every jump keeps the window and the counter together.** For `End`,
   `Home`, a wheel scroll and a tray zoom: after the gesture settles, the page
   the counter names must be one of the pages actually on screen.
7. **Every tool on the shelf does something.** Parameterised over all ten:
   add it to the bar, arm it, use it, and assert *some* observable change —
   a mark, a stroke, an overlay or a request. Snapshot and Measure fail it now.
8. **Every tool's mark survives a reload.** The same ten, extended: what the
   tool creates must still be there after reopening the paper. Text and Flag
   fail it now, and it is the test that would have caught the `mkr` CHECK
   violation before it shipped.
9. **A mark can be unmade.** After creating one, a visible control with a
   non-zero box must remove it, and it must stay removed after a reload.
   Asserting the box is non-zero is the point — the button exists today.
10. **A paper with no text layer disables its text tools.** Render a
    text-free PDF and assert that Select, Highlight, Underline, Strikethrough,
    Note, Ask, Flag and Text all report themselves unavailable with a reason,
    and that the panel's empty state does not tell the student to select a
    line.

Three more that the second pass earned:

11. **A mark that loses its place is listed, not hidden.** Swap the file under
    a paper, reopen, and assert the reader shows the orphaned mark somewhere
    and that its count is not zero. `paper_marks_for` returning a row the
    panel reports as "Marks 0" must fail.
12. **The armed tool's icon clears 3:1.** Screenshot the rail in each livery
    and variant, measure each icon's stroke against its surface, and assert
    3:1. Computed styles are not good enough here — the surfaces are
    translucent, which is how the first attempt at this got it backwards.
13. **Every control is at least 44px** measured as a tap target rather than a
    drawn box, since a transparent `::before` is already paying part of that
    floor and stopping short.

And one that needs a device in the room rather than a test runner: **two-finger
tap undoes on a real iPad.**
